## Current scope

The project has a working authentication and early authorization foundation. It can sign users in, 
keep a server-side session, manage user accounts through protected API endpoints, and check access to 
modules or branches in the permission helper services.

The larger app described in your reference—dashboard, employee and attendance screens, consultancy 
features, accounts, chat, and the senior project’s matching UI—is not implemented in the files we 
inspected. The current React app has a login screen and a temporary signed-in screen.

One detail to keep straight: your reference mentions the senior project’s login as 
Consultancy@gmail.com` / `Shul@123`. The current Spring Boot initializer creates a different 
development account: `admin@consultancy.com` / `Admin@123`. The current code uses the latter.

## The sign-in flow

```text
Login.jsx
  → AuthContext.login()
  → authService.login()
  → POST /api/auth/login
  → AuthController
  → AuthenticationManager
  → CustomUserDetailsService → UserRepository → MySQL
  → verify password hash
  → save authentication in HTTP session
  ← LoginResponse JSON + JSESSIONID cookie
  → React stores user in AuthContext
  → App.jsx displays the signed-in screen
```

On a page reload, React calls `GET /api/auth/me`. The browser sends its session cookie, 
and the backend uses it to identify the current user. Logout invalidates that session.

## Spring Boot backend files

### Configuration

- [DataInitializer.java]
runs at application startup. If `admin@consultancy.com` is not already in the database, it creates a 
`SUPER_ADMIN` user, hashes the password using Spring Security’s password encoder, and saves the account.
 It prints the development credentials to the console.

- [SecurityConfig.java]
configures Spring Security. It defines BCrypt password hashing, connects the authentication 
provider to `CustomUserDetailsService`, permits unauthenticated access to `POST /api/auth/login`, 
and requires authentication for other API requests. It uses an HTTP session to retain login state 
and limits a user to one session. Method-level permission checks are enabled here too.

### Controllers

- [AuthController.java] exposes three endpoints under `/api/auth`:
  - `POST /login` authenticates the submitted email and password, stores the authentication in the
     session, and returns a safe summary of the user.
  - `GET /me` returns that summary for the current session.
  - `POST /logout` clears the security context and invalidates the session.
- [UserController.java] exposes user creation, listing, lookup, update, status change, and deletion
under `/api/users`. The class-level `@PreAuthorize("hasRole('SUPER_ADMIN')")` means these endpoints 
are restricted to super-admin users. A normal signed-in user should receive `403 Forbidden`.

### Request and response DTOs

DTOs define the JSON the API accepts or returns; they keep the API contract separate from the database 
entity.

- [LoginRequest.java] accepts `email` and `password`. Validation requires both fields and checks that 
  the email is formatted as an email address.
- [LoginResponse.java] returns `id`, `name`, `email`, `role`, `branch`, and `accessModules`. 
  It does not return the password hash.
- [CreateUserRequest.java] accepts fields for a new user. Name, valid email, password of at least six
  characters, and role are required.
- [UpdateUserRequest.java] accepts optional fields for a partial update. The service changes only  
  fields supplied with a usable value.
- [UserResponse.java] returns user details such as name, role, branch, status, and access modules. 
  It excludes the password.

### User-management service

[UserService.java] contains the work behind the user endpoints:

- Creates users and rejects an email that already exists.
- Hashes a new or updated password before saving it.
- Normalizes roles to uppercase and checks branch values against `Bramhapuri`, `Chandrapur`, 
`Nagpur`, and `ALL`.
- Defaults a missing role to `USER`, missing branch to `ALL`, and missing status to `ACTIVE`.
- Converts saved user entities into `UserResponse` objects so the password is never sent back.
- Finds, updates, changes status, and deletes users.

The service uses [UserRepository.java] to read and write user records. 
[User.java] maps those records to the `users` database table.

### Security support classes

- [CustomUserDetailsService.java] looks up an account by email when Spring Security tries to 
  authenticate a login.

- [CustomUserDetails.java] adapts your `User` entity to the interface Spring Security expects. It 
  returns the stored password hash and email as the username. Its `getAuthorities()` adds the 
  `ROLE_` prefix, so a stored role such as `SUPER_ADMIN` becomes `ROLE_SUPER_ADMIN` for checks like 
  `hasRole('SUPER_ADMIN')`. Its account-status methods currently always return `true`; the user’s 
  `status` field is not yet used to disable sign-in.

- [AppModule.java] lists module names such as `DASHBOARD`, `ACCOUNTS`, `EMPLOYEE`, `ATTENDANCE`, and 
  `CONSULTANCY`.

- [PermissionService.java] checks whether the authenticated user has a requested module in their 
  comma-separated `accessModules` value. `SUPER_ADMIN` and a user whose modules contain `ALL` pass 
  every module check.

- [Branch.java] lists the branch names as enum constants.

- [BranchPermissionService.java] allows a super-admin or an `ALL`-branch user to access any branch. 
  Other users can access their assigned branch. These helpers only enforce rules when an endpoint 
  calls them—for example, with a method security annotation. Their presence alone does not protect 
  every endpoint.

## React frontend files

- [Login.jsx] renders the email/password form, toggles password visibility, shows errors, disables 
  the submit button while signing in, and calls the `login` function from the auth context.

- [AuthContext.jsx] shares the current user and login/logout functions across React components. On 
  startup it tries `/api/auth/me`; if that fails it treats the user as signed out.

- [authService.js] sends the login, current-session, and logout requests. It sets `credentials: 
  "include"` so the browser sends and receives the `JSESSIONID` session cookie.

- [api.js] defines `API_BASE_URL = "/api"`. The current `authService.js` calls full paths 
  directly, so it does not currently use this constant.

- [App.jsx] waits while the current session is checked, shows the login page when no user is 
  signed in, 
  and otherwise shows a temporary screen with the user’s name, role, branch, and modules. It does not 
  yet implement the dashboard or module-based navigation.
- [main.jsx] starts the React app and mounts `App` into the HTML page.

## Example request and response

Login request:

```http
POST /api/auth/login
Content-Type: application/json

{
  "email": "admin@consultancy.com",
  "password": "Admin@123"
}
```

Successful response:

```json
{
  "id": 1,
  "name": "Admin",
  "email": "admin@consultancy.com",
  "role": "SUPER_ADMIN",
  "branch": "ALL",
  "accessModules": "ALL"
}
```

The session cookie is set separately in the HTTP response headers. The frontend then sends it
 with later requests. The response body does not contain a token.

## What is implemented versus planned

The reference says the super-admin should manage users and decide which sections each user can 
access. **The backend has pieces of this rule**: user-management endpoints require super-admin, 
and module/branch helper services can make checks. The actual dashboard visibility, module navigation, 
and branch-filtered employee/attendance data still need to be connected to real screens and endpoints.

The implementation plan says user management and permissions, followed by authorization and branch
security, then React login/session handling and later product modules. Your reference reports that 
login, session restoration, user management, module checks, and branch checks were exercised. 
The React files now provide login and session handling, but the broader application remains future work.
 The senior PHP project and its MySQL schema are references for that work; they are not automatically 
implemented by these files.
